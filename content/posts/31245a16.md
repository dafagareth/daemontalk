Banyak *founder* dan *engineer* startup AI mengira musuh terbesar biaya infrastruktur mereka adalah **ukuran model LLM** (bobot miliaran parameter). Mereka menghitung anggaran server: *"Model LLaMA-3 70B butuh 140 GB VRAM FP16, berarti cukup sewa 2 unit Nvidia A100 80GB seharga $5.000 per bulan."*

Sebulan kemudian, tagihan cloud mereka meledak hingga **$40.000 (lebih dari 600 juta rupiah)** atau server langsung mengalami *Out of Memory (OOM) Crash* saat baru dipakai 30 pengguna secara bersamaan.

Apa yang salah? Mereka melupakan monster tersembunyi dalam sistem inferensi Transformer: **KV-Cache (Key-Value Cache)**.

## 1. Ilusi Inferensi LLM: Prefill vs. Decoding

Untuk memahami kenapa inferensi LLM itu mahal, kita harus membedakan dua fase kerja model Transformer (*Autoregressive Decoder*):

1. **Fase Prefill (Prompt Processing)**:
   Model memproses seluruh kalimat masukan (*prompt*) pengguna secara paralel dalam satu komputasi matriks besar. Fase ini bersifat **Compute-Bound** (memaksimalkan daya komputasi FLOPS core GPU).
2. **Fase Decoding (Token-by-Token Generation)**:
   Model menghasilkan jawaban **satu kata per satu kata**. Setiap kali 1 token baru diciptakan, token tersebut dimasukkan kembali sebagai masukan untuk menebak token berikutnya. Fase ini bersifat **Memory-Bandwidth Bound**.

> [!NOTE]
> **Mengapa KV-Cache Diperlukan?**  
> Dalam arsitektur *Self-Attention*, token yang baru dihasilkan harus "memperhatikan" (*attend*) seluruh token yang ada sebelumnya. Jika kita tidak menyimpan komputasi vektor dari token terdahulu, GPU harus menghitung ulang matriks *Key* ($K$) dan *Value* ($V$) untuk seluruh kalimat dari awal pada setiap kata baru ($O(N^2)$ komputasi sia-sia).

## 2. Hitungan Matematika Brutal: Di Mana Uang Anda Terbakar?

Berapa sebenarnya ukuran memori KV-Cache yang harus dialokasikan GPU untuk setiap pengguna? Rumus resminya adalah:

$$\text{KV-Cache Per Request} = 2 \times n_{\text{layers}} \times n_{\text{heads}} \times d_{\text{head}} \times \text{seq\_len} \times \text{bytes}$$

Mari kita hitung secara riil menggunakan model **LLaMA-3 70B** dengan *Grouped-Query Attention (GQA)*:
* Jumlah layer ($n_{\text{layers}}$) = 80
* Jumlah KV heads ($n_{\text{heads}}$) = 8
* Head dimension ($d_{\text{head}}$) = 128
* Presisi data (FP16 / BF16) = 2 bytes
* Panjang konteks per sesi ($\text{seq\_len}$) = 8.192 token (8k context)

$$\text{Ukuran KV-Cache per 1 User} = 2 \times 80 \times 8 \times 128 \times 8.192 \times 2 = \mathbf{2,68\text{ MB per User}}$$

Kelihatannya kecil? **Jangan tertipu!**

### Skenario Nyata di Server Produksi:
Bayangkan startup Anda melayani **64 pengguna aktif bersamaan** (*concurrency* 64) dengan dokumen RAG (*Retrieval-Augmented Generation*) panjang (misal 16k context per user):

$$\text{KV-Cache} = 64 \times 5,36\text{ GB} = \mathbf{343\text{ GB VRAM}}$$

| Komponen Memori di GPU | Kebutuhan VRAM | Sifat Memori |
| :--- | :--- | :--- |
| **Bobot Model LLaMA-70B (FP16)** | **~140 GB** | Statis (Tetap) |
| **KV-Cache (64 Pengguna @ 16k Context)** | **~343 GB** | Dinamis (Membengkak) |
| **Total VRAM yang Dibutuhkan** | **$\mathbf{483\text{ GB VRAM}}$** | 💥 **Krisis Infrastruktur** |

> [!WARNING]
> **Fakta Mengerikan:**  
> KV-Cache memakan **lebih dari 70% total kapasitas VRAM server Anda**, jauh melampaui ukuran bobot model itu sendiri. Untuk menampung 64 pengguna ini saja, Anda dipaksa menyewa kluster **8x Nvidia H100 80GB SXM5**.

## 3. Masalah Fragmentasi Memori: Alokasi Statis Konvensional

Masalahnya tidak berhenti pada hitungan matematis di atas. Pada sistem inferensi tradisional (sebelum tahun 2023), server mengalokasikan memori KV-Cache secara **kontigu statis (berurutan)** untuk mengantisipasi batas maksimum konteks (*max sequence length*).

Riset dari tim **UC Berkeley (SOSP 2023)** menemukan bahwa:
* **60% hingga 80% VRAM GPU terbuang sia-sia (*wasted memory*)** akibat *internal fragmentation* dan reservasi slot memori kosong untuk token yang sebenarnya belum tentu dihasilkan oleh LLM.
* Akibatnya, server kehabisan VRAM padahal GPU sebenarnya masih sanggup memproses ribuan komputasi per detik.

## 4. Penyelamat Industri: PagedAttention & vLLM

Pada akhir tahun 2023, sebuah terobosan sistem operasi diterapkan pada inferensi AI oleh tim peneliti dari UC Berkeley melalui proyek open-source **vLLM** dengan algoritma bernama **PagedAttention**.

### Bagaimana PagedAttention Bekerja?
PagedAttention mengadopsi konsep **Virtual Memory dan Page Tables** yang sudah dipakai oleh kernel sistem operasi Linux selama puluhan tahun:

* **KV Blocks Non-Kontigu:** KV-cache dipecah menjadi blok-blok kecil (berukuran 16 atau 32 token) yang dialokasikan secara acak di VRAM sesuai kebutuhan nyata (*on-demand*).
* **Block Translation Table:** Tabel translasi memori mencatat pemetaan logika urutan token ke alamat fisik blok di VRAM GPU.
* **Zero Internal Fragmentation:** Pemborosan memori KV-Cache dipangkas drastis dari **73% menjadi kurang dari 4%**, meningkatkan *throughput* hingga **4x lipat**.

## 5. Tiga Strategi Rekayasa Sistem di Produksi

```callout TIP
Berikut adalah 3 langkah arsitektur wajib bagi systems engineer yang menangani inferensi LLM produksi:
```

1. **Gunakan Grouped-Query Attention (GQA)**:  
   Hindari model dengan *Multi-Head Attention (MHA)* penuh. Model modern seperti LLaMA-3 dan Qwen menggunakan GQA yang membagi 1 KV head untuk 8 Query head, langsung memangkas kebutuhan KV-Cache sebesar **87.5%**.
2. **Terapkan Kuantisasi KV-Cache (FP8 / INT4)**:  
   Alih-alih menyimpan KV-Cache dalam FP16 (2 byte), kuantisasi ke format **FP8** (1 byte) atau **INT4** (0.5 byte) menggunakan *KIVI* atau *vLLM FP8 Cache* untuk melipatgandakan kapasitas *concurrency*.
3. **Aktifkan Prefix / Prompt Caching**:  
   Pada aplikasi RAG atau Chatbot dengan *System Prompt* panjang, simpan KV-Cache dari instruksi berulang agar dapat dipakai bersama antar pengguna tanpa duplikasi memori.
