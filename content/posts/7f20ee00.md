Pernah dengar orang bilang, *"Docker itu semacam Virtual Machine (VM) tapi lebih ringan"*? Hati-hati, penjelasan ini sebenarnya keliru dan bisa menyesatkan pemahaman kita soal arsitektur sistem. 

Container sama sekali tidak menjalankan sistem operasi sendiri, tidak punya kernel bawaan, dan tidak berjalan di atas *hypervisor*. Secara harfiah, container hanyalah **proses biasa** di dalam kernel *host* yang "dibatasi" pandangannya terhadap sistem. Yuk, kita bongkar apa yang sebenarnya terjadi di balik layar.

---

## 1. Masalah yang Diselesaikan Docker

Sebelum membedah mekanismenya, kita perlu paham dulu masalah mendasar yang ingin dipecahkan. Anda pasti pernah mengalami drama *"It works on my machine!"*: aplikasi berjalan mulus di laptop Anda, tapi berantakan saat di-*deploy* ke *server* karena beda versi *library*, konfigurasi, atau dependensi.

Pendekatan lawas untuk masalah ini adalah **Virtual Machine (VM)**. Idenya adalah menjalankan sistem operasi lengkap di dalam sistem operasi lain menggunakan *hypervisor*. Cara ini memang berhasil, tapi sangat "mahal". 

Setiap VM membawa kernelnya sendiri. Akibatnya, proses *booting* bisa memakan waktu hingga hitungan menit dan rakus sumber daya (RAM & CPU). Pendekatan ini jelas kurang cocok untuk *scaling microservices* atau alur kerja *development* yang serba cepat. 

Di sinilah Docker masuk membawa solusi **OS-level virtualization**: berbagi satu kernel *host*, tapi mengisolasi setiap proses sehingga masing-masing merasa berjalan sendirian di mesin tersebut.

## 2. Perbedaan Fundamental dengan Virtual Machine

Perbedaan paling inti ada pada **di lapisan mana isolasi itu terjadi**.

VM menjalankan sistem operasi "tamu" (*guest OS*) yang benar-benar utuh di atas *hypervisor*. Artinya, VM menduplikasi semuanya dari *host*: kernel, *device driver*, hingga *library* sistem. 

Docker tidak melakukan itu sama sekali. Container langsung berbagi pakai kernel milik *host*. Konsekuensinya sangat kentara jika kita bandingkan secara langsung:

| Aspek | Virtual Machine | Docker Container |
| :--- | :--- | :--- |
| **Kernel** | Punya kernel sendiri per VM | Berbagi kernel *host* |
| **Lapisan Isolasi** | *Hypervisor* (level *hardware*) | *Namespace* & *cgroup* (level kernel) |
| **Waktu Start** | Hitungan menit (*boot* OS penuh) | Sub-detik (*start* proses biasa) |
| **Ukuran Image** | Gigabyte (OS lengkap) | Megabyte (hanya dependensi aplikasi) |
| **Overhead Resource**| Tinggi (alokasi statis RAM/CPU) | Rendah (resource dibagi secara dinamis) |

> **Catatan:** Tabel ini bukan untuk menghakimi mana yang lebih baik secara mutlak. VM tetap juara untuk urusan isolasi keamanan tingkat tinggi atau jika Anda perlu menjalankan OS yang berbeda di satu mesin fisik. Tapi untuk kecepatan iterasi dan densitas *deployment*, Docker pemenangnya.

## 3. Kenapa Container Merasa "Sendirian"?

Rahasia isolasi Docker sebenarnya berpijak pada fitur kernel Linux yang bernama **Namespace**. 

Namespace bertugas menipu proses. Ia membuat proses di dalamnya percaya bahwa mereka memiliki *resource* sistem secara eksklusif, padahal *resource* tersebut masih milik kernel *host* yang sama. Docker menggunakan beberapa jenis *namespace* untuk menciptakan ilusi ini:

*   **PID Namespace:** Mengalokasikan deretan PID (*Process ID*) yang independen. Ini sebabnya aplikasi Anda terlihat sebagai PID 1 di dalam container, padahal di *host* ia punya PID yang sama sekali berbeda (misal: PID 3491).
*   **Network Namespace:** Mengelola jaringan secara terpisah (seperti *routing table* privat, IP, *socket*, dan *firewall*). Setiap container bisa punya konfigurasi jaringan sendiri tanpa takut bentrok satu sama lain.
*   **UTS Namespace:** Memungkinkan setiap container punya *hostname* dan nama domainnya sendiri.
*   **Mount Namespace:** Memberi container ilusi bahwa ia punya *filesystem root* (/) sendiri yang terpisah dari *host*, kecuali Anda sengaja membagikannya lewat *Volume*.

Untuk urusan jaringan, Docker biasanya membuat pasangan *Virtual Ethernet (veth pair)*. Satu ujungnya dicolokkan ke *bridge* `docker0` di *host*, dan ujung lainnya ditarik masuk ke *namespace* container. Container merasa punya kartu jaringan fisik (*eth0*), padahal itu cuma "terowongan" menuju *host*.

```text
┌───────────────────────────────┐
│           Host Kernel         │
│                               │
│  ┌──────────┐   ┌──────────┐  │
│  │ Container│   │ Container│  │
│  │  A       │   │  B       │  │
│  │ PID ns   │   │ PID ns   │  │
│  │ NET ns   │   │ NET ns   │  │
│  │ MNT ns   │   │ MNT ns   │  │
│  └────┬─────┘   └────┬─────┘  │
│       │  veth pair   │        │
│       └───────┬──────┘        │
│           docker0 bridge      │
└───────────────────────────────┘
```

## 4. Kenapa Satu Container Nakal Tidak Bisa Menguras Resource?

Kalau *Namespace* mengatur apa yang **terlihat** oleh proses, maka ada satpam lain yang mengatur apa yang **boleh dipakai** oleh proses. Mekanisme ini disebut **Control Groups** atau **cgroups**.

Cgroups adalah pengatur *resource* dari kernel Linux yang menentukan batas maksimal (CPU, memori, I/O) yang boleh dikonsumsi oleh sebuah proses. Tanpa cgroups, satu container yang mengalami *memory leak* bisa dengan mudah menelan seluruh RAM *host* dan membuat layanan lain *crash*.

Di Docker, penerapannya sangat sederhana lewat CLI:

```bash
docker run -it --memory="1g" --cpus="1.0" ubuntu
```

Perintah di atas secara otomatis memberitahu Docker Engine untuk membatasi container tersebut agar maksimal hanya menggunakan 1 GB RAM dan 1 *core* CPU. Docker mendelegasikan batasan ini langsung ke kernel.

## 5. Rahasia Image yang Bisa Dipakai Berulang

Ada satu hal lagi yang membedakan container dari sekadar "proses yang diisolasi", yaitu bagaimana *image* disusun. Docker menggunakan sistem **Union Filesystem** (biasanya *OverlayFS*). 

Setiap baris instruksi di `Dockerfile` menghasilkan sebuah *layer* baru. *Layer-layer* ini bersifat *read-only* (hanya-baca) dan bisa dibagikan dengan *image* lain yang menggunakan fondasi yang sama. 

Saat Anda menjalankan container, Docker tidak menyalin seluruh isi *image*. Ia hanya menempelkan satu *layer* transparan tipis di tumpukan paling atas yang bersifat *read-write* (*copy-on-write*). Inilah sebabnya menjalankan 10 container dari *image* yang sama tidak akan memakan *disk space* 10 kali lipat; hanya *layer* teratas yang unik untuk tiap container.

## 6. Siapa yang Sebenarnya Mengeksekusi Ini Semua?

Fakta menarik: Docker Engine itu tidak langsung membuat *namespace* dan *cgroup*. Tugas kotor ini diserahkan kepada **Container Runtime**, seperti `containerd` dan `runc`. 

Alur kerjanya kira-kira seperti ini:
1. Anda mengetik perintah `docker run`.
2. Docker CLI mengirim perintah itu ke Docker Daemon.
3. Daemon meneruskannya ke **containerd** (manajer siklus hidup container).
4. `containerd` memanggil **runc** (implementasi standar dari *Open Container Initiative* / OCI).
5. `runc`-lah yang berinteraksi langsung dengan kernel untuk membuat *namespace* dan *cgroup*, lalu menjalankan proses Anda.

Memahami lapisan ini penting. Container bukanlah teknologi eksklusif milik Docker; ia adalah kombinasi fitur bawaan kernel Linux dengan standar OCI. Docker "hanyalah" alat populer yang membungkus itu semua agar mudah kita gunakan.

## 7. Kesimpulan: Container Itu Proses, Bukan Mesin

Kembali ke poin utama: **Docker container pada dasarnya hanyalah proses Linux biasa**. 

Tidak ada kernel tersembunyi, tidak ada *hypervisor*, dan tidak ada OS tamu. Ia terlihat seperti "mesin mini" murni karena kombinasi manipulasi pandangan lewat *namespace* dan pembatasan daya lewat *cgroup*, yang lalu dibungkus rapi dalam sistem *file* berlapis.

Dengan memahami konsep ini, cara Anda membaca *error* akan berubah total:
*   Jika container mati dengan status `OOMKilled`, itu bukan *"bug Docker yang aneh"*, melainkan *cgroup* yang sedang bekerja mematikan proses karena melewati batas RAM.
*   Jika container tidak bisa diakses dari jaringan luar, itu bukan *"Docker yang error"*, melainkan sifat bawaan *Network Namespace* yang memang terisolasi secara *default*.

### Pertanyaan yang Sering Muncul (FAQ)

**Q: Kalau container berbagi kernel *host*, apakah container Windows bisa jalan di OS Linux?**
> Secara *native*, **tidak**. Karena container bergantung pada kernel *host*, container Linux butuh kernel Linux, dan container Windows butuh kernel Windows. Docker Desktop mengakali hal ini dengan cara memutar kernel Linux di dalam VM ringan (lewat WSL2 atau Hyper-V) secara diam-diam di belakang layar laptop Mac/Windows Anda.

**Q: Apakah keamanan container seketat Virtual Machine?**
> **Tidak secara *default*.** Karena container memakai kernel yang sama dengan *host*, celah keamanan di level kernel (*kernel exploit*) bisa berdampak pada seluruh container di mesin tersebut. Ini sebabnya sistem dengan kebutuhan privasi ekstra ketat biasanya tetap memakai VM, atau menggunakan metode *hybrid* seperti gVisor dan Kata Containers.
