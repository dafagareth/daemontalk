Di lingkungan berbagi (*shared environment*) seperti server praktikum terpusat, mahasiswa sering kali berbagi sumber daya komputasi yang sama. Dalam skenario ini, bukan hal yang aneh jika satu proses tunggal memonopoli CPU dan memori, menyebabkan server menjadi lambat atau bahkan mogok sepenuhnya. Masalah ini paling sering dipicu oleh sebuah kode skrip yang mengalami kebocoran memori (*memory leak*) atau terjebak dalam kalang tak berhingga (*infinite loop*) yang tak sengaja dibuat oleh mahasiswa saat mengerjakan tugas praktikum algoritma.

Ketika sebuah proses terus-menerus meminta alokasi RAM tanpa henti, kernel Linux akan kehabisan ruang untuk mengelola operasi dasar sistem operasi. Pada titik kritis tersebut, kernel akan memicu modul pencegahan bencana bernama *Out-Of-Memory (OOM) Killer*. Modul ini akan menghitung "skor keburukan" (badness score) dari setiap proses yang berjalan, dan secara paksa mematikan proses yang dianggap paling banyak menghabiskan memori. Ironisnya, OOM Killer dapat secara acak mematikan proses sah milik individu lain, basis data, atau layanan penting lainnya, padahal mereka tidak melakukan kesalahan apa pun.

Pada masa lampau, administrator sistem kampus sering kali mengandalkan perintah pembatasan level pengguna (*ulimit*) untuk membatasi pemakaian RAM setiap akun. Namun, pendekatan ini memiliki keterbatasan besar dan sudah usang karena pembatasan ulimit tidak selalu efektif menangani sistem turunan yang kompleks atau hierarki proses *multithreaded* modern.

Infrastruktur tingkat produksi (*production-grade*) saat ini mengandalkan Control Groups (`cgroups`). Fitur kernel Linux ini memungkinkan administrator untuk mengalokasikan, memprioritaskan, dan membatasi sumber daya (CPU, memori, I/O disk, hingga jaringan) secara ketat pada sebuah kelompok proses hierarkis. Teknologi inilah yang juga menjadi tulang punggung dari perangkat lunak kontainerisasi modern seperti Docker dan Kubernetes.

Dengan menetapkan *cgroups* per sesi terminal atau berdasarkan identitas pengguna (*UID*), beban komputasi diisolasi secara adil. Jika mahasiswa A menjalankan skrip Python yang memakan banyak memori, proses tersebut hanya dapat mengonsumsi RAM maksimum sesuai batas *cgroup* miliknya. Ketika batas tersebut terlampaui, kernel hanya akan membunuh (melalui *OOM kill*) proses di dalam kelompok mahasiswa A saja, menjaga keseluruhan stabilitas server dan terminal mahasiswa lainnya secara holistik.

Untuk memeriksa parameter pengaturan memori *cgroup* v2 pada sistem Anda saat ini, Anda bisa membaca dari berkas antarmuka virtual *sysfs*:

```bash
# Menampilkan batas maksimum alokasi memori untuk sesi cgroup pengguna saat ini
cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/memory.max

# Menampilkan penggunaan memori aktual dalam satuan byte
cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/memory.current
```

Pada level sistem berbasis *systemd*, penerapan *cgroups* dapat dilakukan secara elegan tanpa skrip yang rumit. Administrator dapat membuat berkas konfigurasi *drop-in* di direktori `/etc/systemd/system/user-.slice.d/` untuk memberikan batas keras (hard limit) alokasi RAM per pengguna:

```ini
[Slice]
MemoryMax=1G
CPUQuota=50%
```

Membiasakan diri dengan konsep pembatasan sumber daya dan isolasi sangat krusial bagi mahasiswa ilmu komputer. Pola pikir yang beralih dari "yang penting kode saya berjalan" menjadi "bagaimana kode saya beroperasi dalam ekosistem sistem yang terbatas" adalah ciri khas transisi dari kebiasaan praktikum amatir ke tingkat kerekayasaan perangkat lunak profesional.
